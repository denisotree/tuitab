# MCP-сервер

> 🇬🇧 [This page in English](../en/mcp.md) · [← Оглавление документации](README.md)

`tuitab --mcp` превращает бинарник в сервер [Model Context Protocol](https://modelcontextprotocol.io).
Ассистент, которому дали файл с данными, считает по нему движком tuitab, а не в уме.

Смысл узкий, и его стоит назвать прямо: **языковая модель, которую попросили
сложить колонку, выдаст правдоподобное число.** Отправить вопрос настоящему
движку и прочитать ответ — это разница между отчётом, по которому можно
действовать, и отчётом, который придётся перепроверять.

## Подключение

**Claude Code** — одной командой:

```sh
claude mcp add tuitab -- tuitab --mcp
```

Добавьте `-s user`, чтобы сервер был доступен во всех проектах, а не только в
текущем.

**Claude Desktop** — `~/Library/Application Support/Claude/claude_desktop_config.json`
на macOS, `%APPDATA%\Claude\claude_desktop_config.json` на Windows:

```json
{
  "mcpServers": {
    "tuitab": {
      "command": "/opt/homebrew/bin/tuitab",
      "args": ["--mcp"]
    }
  }
}
```

Полный путь важнее, чем кажется: приложение стартует не из вашей оболочки и может
не видеть `PATH`. Свой путь покажет `which tuitab`.

**Cursor, Windsurf, Zed** — тот же блок в их `mcp.json`.

**Что угодно ещё** — это обычный stdio-сервер. Запускаете подпроцессом, пишете в
stdin JSON-RPC по строке на сообщение, читаете ответы из stdout. Принимаются
версии протокола `2025-06-18`, `2025-03-26` и `2024-11-05`.

## Проверка

Вообще без клиента:

```sh
printf '%s\n' \
 '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"t","version":"0"}}}' \
 '{"jsonrpc":"2.0","method":"notifications/initialized"}' \
 '{"jsonrpc":"2.0","id":2,"method":"tools/list"}' | tuitab --mcp
```

Во втором ответе — список инструментов: четыре, или шесть с `--mcp-write`.
В Claude Code то же покажет `/mcp`.

## Инструменты

| Инструмент | На что отвечает |
|------------|-----------------|
| `tuitab_inspect` | Что в файле — листы, таблицы и view, имена колонок, выведенные типы, число строк, несколько строк примера. Для базы данных ещё объявленный SQL-тип каждой колонки, NOT NULL, PRIMARY KEY и DEFAULT, `CREATE`-стейтмент и размеры каждой таблицы |
| `tuitab_query` | Всё вычислительное, конвейером операций |
| `tuitab_describe` | Статистический профиль каждой колонки |
| `tuitab_jq` | jq-программа по вложенным JSON, JSONL, YAML или TOML |
| `tuitab_calc` | Любые расчёты, с файлом или без — см. [Расчёты](#расчёты) |

`tuitab_inspect` идёт первым в любом сценарии. Имена колонок, угаданные по имени
файла, ошибочны достаточно часто, чтобы стоить лишнего обращения. Он принимает
`sample_rows` (по умолчанию 5), если пяти строк мало или много.

Все инструменты, читающие файл, принимают один и тот же `source`: `path`, плюс `container` для
листа или таблицы, `delimiter` — перекрыть автоопределение разделителя CSV, и
`format` — перекрыть расширение (`{"path": "deploy.conf", "format": "yaml"}`).
Голая строка с путём тоже работает. `tuitab_describe` принимает `columns`, чтобы
профилировать только часть; `tuitab_query` — `output.limit` (по умолчанию 100
строк).

Запущенный с `--mcp-write`, сервер даёт ещё два — `tuitab_write` и
`tuitab_write_apply`, — и тогда действует всё из раздела [Как изменить то, что
уже есть](#как-изменить-то-что-уже-есть). Без флага их просто нет, а вызов по
имени отвечает, каким флагом они включаются.

## Операции

`tuitab_query` принимает `source` и список `ops`, применяемых по порядку — каждая
к результату предыдущей.

```json
{
  "source": {"path": "/data/sales.xlsx", "container": "Q3"},
  "ops": [
    {"filter": [{"col": "status", "op": "eq", "value": "closed"}]},
    {"compute": {"name": "margin", "expr": "revenue - cost"}},
    {"group_by": {"by": ["region"], "agg": [{"col": "margin", "fn": "sum"}]}},
    {"sort": {"by": [{"col": "margin:sum", "desc": true}]}}
  ]
}
```

| Операция | Примечания |
|----------|------------|
| `filter` | Элементы объединяются через AND. Операторы: `eq`, `ne`, `gt`, `ge`, `lt`, `le`, `in`, `not_in`, `contains` (регулярное выражение), `between`, `is_empty`, `not_empty` |
| `select` | Оставить эти колонки в этом порядке |
| `sort` | `{"col": …, "desc": …}` для одного ключа, `{"by": [{…}, {…}]}` для нескольких |
| `compute` | Вычисляемая колонка из выражения |
| `group_by` | Ровно запрошенные агрегаты в запрошенном порядке |
| `aggregate` | Общий итог — одна строка, без группировки |
| `frequency` | Распределение по частоте, с колонками `Count` и `Pct` |
| `pivot` | Строки по `index`, колонки по `on`, ячейки по `formula` |
| `join` | С другим файлом, `how`: inner / left / right / outer / anti / semi / diff. anti и semi оставляют столбцы этой таблицы и считают NULL-ключи равными. diff сравнивает таблицы как `git diff`: первый столбец `_diff` содержит `=` `~` `-` `+`, а `<col>_right` — значения другой таблицы в строках `~`. Ключи должны быть уникальны с обеих сторон |
| `dedup` | По одной строке на ключ. `keep`: first, last, min, max, random |
| `duplicates` | Только строки, чей ключ повторяется |
| `sample` | `n` случайных строк |
| `window` | Колонка, вычисленная из строк вокруг каждой строки. `order_by` задаёт порядок внутри окна, не меняя порядок таблицы |
| `transpose` | Таблица на попа, или одна её строка |
| `limit` | Первые `n` строк |

Для OR альтернативы заворачиваются в `any_of`:

```json
{"filter": [
  {"any_of": [{"col": "region", "op": "eq", "value": "North"},
              {"col": "region", "op": "eq", "value": "South"}]},
  {"col": "amount", "op": "gt", "value": 1000}
]}
```

что читается как `(North OR South) AND amount > 1000`. Один уровень вложенности.

Чтобы сравнить две колонки, поставьте колонку туда, где стоял бы литерал:

```json
{"col": "revenue", "op": "gt", "value": {"col": "cost"}}
```

`HAVING` из SQL — это `filter` после `group_by`.

`ops` можно не передавать вовсе — тогда результат это сама таблица, как она есть.
Именно этого просит копирование одного файла в другой.

Колонку, в имени которой есть пробел, в выражении пишут в обратных кавычках:
`` {"compute": {"name": "pay", "expr": "`к выплате` * 1.2"}} ``. Двойные кавычки —
это **текстовый литерал**, поэтому `"к выплате" * 1.2` считает по словам, а не по
колонке; такое теперь отвергается, а не отвечает колонкой из NULL. `"3" * 1`
по-прежнему работает — так из текстовой колонки достают число.

### Несколько вопросов одним вызовом

`pipelines` прогоняет их список по одной загрузке файла:

```json
{"source": {"path": "/data/sales.csv"},
 "pipelines": [
   {"name": "by_region", "ops": [{"frequency": {"by": ["region"]}}]},
   {"name": "totals",    "ops": [{"aggregate": [{"col": "amount", "fn": "sum"}]}]}
 ]}
```

Ответ — `{"results": [...]}`, каждая запись со своим `name`. Сбой одного
конвейера не уносит остальные: у него будет `error`, у соседей — их строки. Если
упали все, ошибкой становится весь вызов; одиночный `ops` падает целиком, как и
раньше.

### Оконные функции

```json
{"window": {"fn": "rank", "col": "salary", "over": ["department"],
            "as": "rank_in_dept", "desc": true}}
```

`row_number`, `rank`, `dense_rank`, `cum_sum`, `lag`, `lead`, агрегаты партиции
`sum` / `avg` / `min` / `max` / `count`, размноженные по её строкам, и
`pct_of_total`.

`over` перезапускает окно на каждой группе; без него окно — вся таблица.

`order_by` задаёт, что значит «до», для `cum_sum`, `lag`, `lead` и `row_number` —
четырёх функций, читающих строки по порядку:

```json
{"window": {"fn": "cum_sum", "col": "amount", "order_by": ["date"],
            "over": ["region"], "as": "running_total"}}
```

Порядок применяется **только к окну**: ответ возвращается к тем строкам, где они
и стояли, сама таблица не трогается. Совпадающие значения сохраняют взаимный
порядок, пустые уходят в конец — один и тот же вопрос дважды даёт один ответ.
`desc` разворачивает порядок.

Без `order_by` эти четыре читают кадр как есть, то есть в том порядке, в каком
файл случайно записан. Остальные восемь `order_by` отвергают, а не игнорируют:
сумма не зависит от порядка слагаемых, а ранг упорядочивает по значению,
которое читает.

Для доли внутри группы берите `window` с `over`, для доли от всей таблицы —
`compute` с `amount / sum(amount)`.

## Расчёты

Не каждый вопрос про таблицу. Платёж по кредиту, процентное изменение, среднее
чисел, которые прислал пользователь, — такую арифметику модель считает в уме так же
ненадёжно, как сумму по колонке. `tuitab_calc` принимает выражения текстом и
вычисляет их:

```json
{"steps": [
  {"name": "rate",    "expr": "0.12 / 12"},
  {"name": "payment", "expr": "pmt(rate, 360, 250000)"},
  {"name": "total",   "expr": "round(payment * 360, 2)"}
]}
```

Шаг может использовать имена предыдущих шагов, и значение каждого шага
возвращается — модель цитирует промежуточные результаты, а не переписывает их между
вызовами. Одиночное `{"expr": "…"}` тоже работает.

**Числа десятичные**, 28 значащих цифр, а не float: `0.1 + 0.2` — это `0.3`, и
денежная сумма не уплывает на доли копейки. Значения возвращаются строками, чтобы
ни одна цифра не потерялась в JSON, и у каждого есть `precision`:

| `precision` | Значение | Примеры |
|-------------|----------|---------|
| `exact` | Ни одна цифра не потеряна | `0.1 + 0.2`, `1.07^10`, `round(x, 2)`, `stdev_p(…)` из полных квадратов |
| `rounded` | Десятичное, округлённое до 28 значащих цифр | `1/3`, `sqrt(2)`, `pi`, всё, что посчитано из округлённого значения |
| `approximate` | Плавающая точка, около 15 цифр | `ln`, `exp`, `norm_cdf`, тригонометрия, дробные степени, `irr`, результаты за пределами ±7.9·10²⁸ |

| Что | Доступно |
|-----|----------|
| Операторы | `+ - * / %`, `^` (или `**`; правоассоциативный, `-2^2` — это `-4`), `== != < > <= >=`, `and or not`, скобки, списки `[1, 2, 3]` |
| Константы | `pi`, `e` |
| Математика | `abs`, `round(x[, places])` (половина — от нуля; отрицательные places округляют до десятков, сотен…), `floor`, `ceil`, `trunc`, `sqrt`, `exp`, `ln`, `log10`, `log(x[, base])`, `sin cos tan asin acos atan` (радианы), `radians`, `degrees`, `min`, `max`, `factorial`, `gcd`, `lcm`, `if(cond, a, b)` |
| Статистика | `sum`, `product`, `count`, `mean`/`avg`, `median`, `variance` и `stdev` (выборочные), `var_p` и `stdev_p` (по генеральной совокупности), `percentile(list, p)` с `p` от 0 до 1 (как `PERCENTILE.INC`) — принимают числа, списки или и то и другое. `norm_cdf(z)`, `norm_inv(p)`, `erf`, `erfc` для стандартного нормального распределения: p-value и критические значения. `holm(p-values)` и `bh(p-values)` возвращают список с поправкой на множественные сравнения (Холм–Бонферрони и Бенджамини–Хохберг) в исходном порядке |
| Распределения | `t_cdf(x, df)`, `t_inv(p, df)` (Стьюдент), `chi2_cdf(x, df)`, `chi2_inv(p, df)`, `poisson_cdf(k, mean)`, `binom_cdf(k, n, p)`. CDF — это P(X ≤ x); p-value верхнего хвоста — `1 - …_cdf(…)`, и ниже примерно 10⁻¹⁵ он не опускается |
| Финансы | `pmt(rate, nper, pv[, fv[, type]])`, `fv(rate, nper, pmt[, pv[, type]])`, `pv(rate, nper, pmt[, fv[, type]])`, `npv(rate, flows…)`, `irr(flows[, guess])` — сигнатуры и знаки как в электронных таблицах: выплаченные деньги отрицательны |

Ошибка называет шаг и говорит, что не так: `b (a + c): unknown name 'c' — earlier
steps: a`, `division by zero`, `'=' is not an operator here: compare with '=='`.
Имя шага не может совпадать с функцией или константой.

## Много файлов сразу

Путь может быть паттерном, и всё, что он находит, читается как одна таблица — в
отсортированном порядке:

```json
{"source": {"path": "/data/monthly/*.csv"}}
{"source": {"path": "/site/content/**/index.md"}}
```

Файлы должны держать одни и те же колонки; тот, что выбивается, будет назван, а не
подмешан в таблицу с дырами. Паттерн, не нашедший ничего, отвечает `glob matched no
files: …` — паттерн верный, файлов нет, и это другая беда, чем неверный путь.

`?` и `[abc]` тоже работают. Относительный паттерн считается от каталога, где запущен
сервер, — как и обычный путь.

### Markdown-страница как строка

Страница — это запись: поля frontmatter становятся колонками, текст страницы —
колонкой `body`, а `file` — путь, откуда она пришла. Читаются и YAML между `---`, и
TOML между `+++`; `---` внутри текста — это горизонтальная черта, а не закрывающий
забор.

```json
{"source": {"path": "/site/content/ru/teas/*/index.md"},
 "ops": [{"filter": [{"col": "draft", "op": "ne", "value": true}]},
         {"aggregate": [{"col": "*", "fn": "count"}]}]}
```

Страницы не обязаны нести одинаковые поля — отсутствующее приходит как NULL, ровно
как в списке JSON-объектов. Благодаря этому статический сайт сверяется с базой одним
вызовом, а не через скрипт-экспортёр.

## Как читать ответы

Строки приходят массивами, соответствующими списку `columns`:

```json
{
  "columns": [{"name": "region", "type": "string"},
              {"name": "amount:sum", "type": "float"}],
  "rows": [["North", 563001.5], ["South", 480000.5]],
  "row_count": 2, "returned": 2, "truncated": false
}
```

- **Проценты приходят долями.** `0.42` это 42%.
- **Валюта и дробные — сырые числа**, а не отформатированные строки:
  форматирование нужно человеку, читающему файл, а не модели, которая считает.
- **`truncated` важен.** Когда он `true`, вы видите часть ответа.

## Как получить файл

`output.path` записывает результат вместо возврата строк:

```json
{"output": {"path": "/data/report.xlsx"}}
```

Расширение выбирает формат — `.xlsx`, `.csv`, `.tsv`, `.parquet`, `.arrow`,
`.json`, `.jsonl`, `.yaml`, `.toml`, `.sqlite`, `.duckdb`. В отличие от JSON
выше, файл для чтения человеком **как раз** отформатирован: символы валюты,
фиксированные знаки после запятой. База данных — нет: она пишется для следующего
запроса, с типизированными колонками, и NULL остаётся NULL.

Годится для всего, что пользователь хочет сохранить, и для результатов, слишком
больших, чтобы их возвращать.

Для `.sqlite` и `.duckdb` таблицу называет `output.table` (по умолчанию
`result`):

```json
{"output": {"path": "/data/shop.db", "table": "products"}}
```

Добавление таблицы не трогает те, что уже в файле, поэтому базу можно собирать
несколькими вызовами, ничего не включая дополнительно.

## Как изменить то, что уже есть

Создание — один вызов. **Изменение того, что у пользователя уже есть — таблицы
или файла — требует `--mcp-write` и происходит в два шага.** Первый говорит, что
именно произойдёт, и не пишет ничего; второй выполняет ровно это.

Причина в форме клиента: модели нельзя показать подтверждающее окно терминала, а
там, где она работает без присмотра, ответ читать тоже некому. Второй осознанный
вызов — единственная преграда, которая не зависит от того, как повела себя
модель.

**Строки в таблице** — `tuitab_write` планирует, `tuitab_write_apply` выполняет:

```json
{"source": {"path": "/data/shop.db", "container": "orders"},
 "set": {"status": "archived"},
 "where": [{"col": "id", "op": "in", "value": [3, 7, 11]}]}
```

в ответ придут сами statements, `rows_matched`, эти строки как они есть сейчас, и
`plan_id`. Прочитайте их пользователю, затем:

```json
{"plan_id": "write-1"}
```

Одно изменение за вызов: `set`, `delete` (которому всегда нужен `where`),
`insert` или `alter` для добавления, удаления и переименования колонок. Фильтр
разрешается в настоящие rowid, а не подставляется в SQL, и `apply` отказывает,
если таблица изменилась с момента плана — тогда не пишется ничего и всё
начинается заново. Любой новый план отменяет предыдущий.

В `insert` колонка без значения — пропущенная или переданная как `null` — не
попадает в statement, поэтому срабатывает `DEFAULT` из схемы; колонка без
`DEFAULT` получает NULL. Значит, `DEFAULT` перебивает явный `null`; чтобы всё же
записать NULL в такую колонку, вставьте строку и затем измените её через `set`.

**Таблица целиком или файл** — то же рукопожатие, вход через `output`:

```json
{"output": {"path": "/data/shop.db", "table": "products", "overwrite": true}}
```

Замена таблицы отвечает statements `DROP`, `CREATE` и `INSERT`, числом строк в
старой таблице против числа в новой и предупреждениями про каждый индекс, триггер
и вьюху, которые уйдут вместе с ней. Перезапись обычного файла отвечает его
размером и временем последней записи. Ни то, ни другое ничего не пишет, пока план
не выполнит `tuitab_write_apply`.

Без `output.overwrite` отказ называет, что на кону — `'inventory' already exists
and holds 47 rows`, — а не флаг, которым это делается.

Запрос не может писать в файл, который он читал.

## Обо что спотыкаются

**Пути разрешает сервер, а не модель.** Относительный путь считается от того
каталога, где клиент запустил процесс, а это редко там, где данные. Давайте
абсолютные пути.

**Базе данных `container` нужен всегда.** `tuitab_inspect` без него перечислит
таблицы и view, а любой другой вызов будет отклонён — `'shop.db' holds 4 tables
and views; pass 'container' to pick one`, — потому что база без названной
таблицы это листинг, а не данные. С `.xlsx` мягче: без `container` он перечислит
листы.

**Каталог перечисляет свои файлы.** Он их не читает — для этого есть паттерн.
Листинг нужен, чтобы осмотреться; `dir/*.csv` — чтобы посчитать по тому, что там
лежит.

**У вложенности есть предел.** `tuitab_query` сплющивает JSON, YAML и TOML в
таблицу. Когда структура глубже, чем это переживает, `tuitab_jq` принимает
jq-программу.

**Случайные результаты сообщают своё семя.** `sample` или `dedup` без `seed`
возвращают то, которое выпало, — передав его обратно, вы получите тот же ответ.

## Чего он не сделает

Здесь нет ни SQL, ни произвольного кода — `tuitab_calc` читает замкнутый язык
арифметики, а не язык программирования. Модель отправляет структурированные
операции, каждая из которых ложится на функцию, уже существовавшую в tuitab, и
получает числа, посчитанные Polars. Это осознанное ограничение, а не
недоделанность: операция, проверенная по схеме, падает громко, когда она неверна,
а строка SQL с опечаткой тихо возвращает неверное число.

Не поддерживаются: подзапросы, self-join и SQL в любом виде. Модель не пишет SQL
даже когда меняет таблицу: statements составляет tuitab и показывает их, а дело
модели — пересказать их и применить план по имени.
